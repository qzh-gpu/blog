# JVM 垃圾回收详解

## 怎么判断对象已死？

### 1. 引用计数法
每个对象维护一个引用计数器，被引用 +1，引用失效 -1，为 0 时回收。
- ❌ **Java 不用此法**：无法解决循环引用问题

### 2. 可达性分析（GC Roots）
从 **GC Roots** 出发，通过引用链能到达的对象是存活的，不可达的可以回收。

**GC Roots 包括**：
- 虚拟机栈（栈帧中的本地变量表）引用的对象
- 方法区中静态属性引用的对象
- 方法区中常量引用的对象
- 本地方法栈中 JNI 引用的对象
- 活跃线程

## 垃圾回收算法

### 标记-清除（Mark-Sweep）
```
标记存活对象 → 清除未标记对象
缺点：产生内存碎片
```

### 标记-复制（Mark-Copy）
```
将内存分为两块，只用一块 → GC 时将存活对象复制到另一块，整块清理
优点：无碎片，效率高
缺点：浪费一半内存
```

### 标记-整理（Mark-Compact）
```
标记存活对象 → 将所有存活对象向一端移动 → 清理边界外的内存
优点：无碎片，不浪费内存
缺点：移动对象开销大
```

---

## 分代收集理论

JVM 将堆分为 **年轻代** 和 **老年代**，针对不同区域使用不同算法。

| 区域 | 特点 | 采用算法 |
|------|------|----------|
| 年轻代 (Young Gen) | 对象朝生夕死，存活率低 | 标记-复制 |
| 老年代 (Old Gen) | 对象存活率高 | 标记-清除 / 标记-整理 |

## 常见垃圾收集器

```java
// JDK 8 默认：Parallel Scavenge + Parallel Old
// JDK 11+ 默认：G1
// JDK 17+ 低延迟选择：ZGC
```

| 收集器 | 特点 | 停顿 | 适用 |
|--------|------|------|------|
| Serial | 单线程，简单 | 高 | 客户端 |
| Parallel | 多线程，吞吐量优先 | 中 | 后台计算 |
| CMS | 并发标记清除 | 低 | 互联网应用(已废弃) |
| **G1** | 区域化分代，可预测停顿 | 可控 | **主流选择** |
| **ZGC** | 超低延迟，TB级堆 | <1ms | 低延迟场景 |

## 常用 JVM 调优参数

```bash
# 堆大小
-Xms2g -Xmx4g                    # 初始堆 2G，最大堆 4G

# 年轻代与老年代比例
-XX:NewRatio=2                   # 老年代:年轻代 = 2:1

# G1 收集器
-XX:+UseG1GC                     # 启用 G1
-XX:MaxGCPauseMillis=200         # 目标最大停顿 200ms

# GC 日志
-Xlog:gc*:file=gc.log:time,level,tags

# 内存溢出 dump
-XX:+HeapDumpOnOutOfMemoryError
-XX:HeapDumpPath=/path/to/dump
```

## 总结

- 理解 GC 原理是 Java 工程师的基本功，面试高频考点
- G1 是 JDK 9+ 的默认收集器，平衡了吞吐量和延迟
- 调优原则：**不要过早优化，先压测再调参**
